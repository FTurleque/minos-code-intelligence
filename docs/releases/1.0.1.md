## Défaut corrigé depuis 1.0.0

Le runtime Windows 1.0.0 pouvait échouer au bootstrap MCP avec :

```text
java.lang.NoClassDefFoundError: org/w3c/dom/Node
```

Le runtime 1.0.1 est dérivé du fat JAR exact avec JDK 24 :

```text
fat JAR
→ jdeps --print-module-deps
→ jpackage --add-modules
→ runtime/bin/java --list-modules
→ contrôle des modules racines
→ assertion java.xml
```

`RUNTIME-MODULES.txt` et `VERSION` conservent les preuves de provenance du runtime.

## Runtime MCP

Le point d'entrée stable reste :

```text
minos.exe mcp
```

Il route vers :

```text
native | docker
```

sans logique Docker dans les configurations Copilot/Claude/Codex et sans fallback silencieux.

Le smoke de release utilise le client officiel MCP Java SDK et valide réellement :

```text
initialize
→ tools/list
→ outils MINOS attendus
```

sur le runtime packagé puis sur le setup installé. Le budget du probe est appliqué à la fois au timeout des requêtes et au timeout d'initialisation du SDK. Le client de smoke utilise son lifecycle `AutoCloseable` pour éviter les fermetures gracieuses longues d'un serveur STDIO volontairement long-lived.

## Désinstallation et ownership

La désinstallation :

- supprime uniquement les intégrations encore détenues par MINOS ;
- préserve les entrées tierces ;
- conserve `%LOCALAPPDATA%\MINOS` par défaut ;
- propose une purge explicite en mode interactif ;
- ne supprime jamais une base PostgreSQL externe ;
- neutralise la purge et les mutations globales dans les smokes automatisés.

## Conflit de tag à résoudre avant publication

Un ancien tag Git :

```text
v1.0.1
```

existe déjà sur :

```text
2de847bdc6bc39e63715f20987a30f07731cc717
```

Ce commit est antérieur au hardening final et **ne constitue pas le candidat 1.0.1**.

Le workflow de publication effectue le préflight du tag avant les builds lourds et refuse :

- de déplacer un tag existant ;
- d'écraser une GitHub Release existante ;
- de publier depuis un checkout différent du SHA attendu.

La résolution de ce tag doit être une décision explicite du mainteneur avant publication. Aucun nettoyage automatique du tag n'est autorisé.

## Contrôles humains restants avant décision

Les smokes CI ne remplacent pas les contrôles utilisateur réels suivants :

- ordre et lisibilité du wizard ;
- résumé final fidèle aux choix ;
- mode natif sélectionné sans Docker ;
- mode Docker sélectionné avec Docker disponible ;
- affichage correct des clients détectés/indisponibles ;
- intégration réelle avec les clients installés chez le mainteneur ;
- état `Connected` dans au moins un client MCP réel ;
- outils MINOS visibles depuis ce client ;
- upgrade réel si une installation antérieure est présente ;
- désinstallation interactive avec **Non / conserver** ;
- désinstallation interactive avec **Oui / purge** ;
- vérification qu'aucune configuration tierce non détenue n'est supprimée.

## Gate de décision

Les gates automatisés sont acquis sur la promotion de readiness. La décision finale porte donc sur :

```text
[x] Plugin Verifier exact-head readiness PASS
[x] Windows Installer exact-head readiness PASS
[x] PR Validation exact-head readiness PASS
[x] OSV exact-head readiness PASS
[x] SonarCloud PASS
[ ] validation utilisateur réelle PASS
[ ] conflit du tag v1.0.1 résolu explicitement
[ ] autorisation explicite de publication donnée
```

Après ces trois derniers points seulement, le workflow manuel `Publish Windows Release` peut être déclenché depuis `main`. Il reconstruira et requalifiera les artefacts sur le SHA exact de `main` avant création de la GitHub Release.
