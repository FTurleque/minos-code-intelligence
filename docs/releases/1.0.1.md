# MINOS 1.0.1 — Windows Release Hardening

Statut : **CANDIDAT EN PRÉPARATION — NON PUBLIÉ**

Branche de maintenance d'origine : `fix/v1.0.1-release-hardening`. Les durcissements M29 sont développés sur `m29-autonomous-docker-runtime` et ne changent pas le fait qu'aucun tag `v1.0.1` ni aucune GitHub Release 1.0.1 ne doivent être créés avant validation locale et utilisateur du setup final.

## Objectif

1.0.1 corrige le packaging/runtime Windows et durcit le parcours MCP. M29 ajoute le backend Docker autonome et son lifecycle, mais **aucun claim de parité native/Docker n'est autorisé avant M29-S8**.

## P0 — runtime Java Windows complet

Cause du défaut 1.0.0 : le runtime `jpackage` était construit à partir d'une liste de modules trop étroite. Le MCP demandait notamment `org.w3c.dom.Node`, fourni par `java.xml`, absent de l'image embarquée.

Correction 1.0.1 :

```text
fat JAR exact
→ JDK 24 jdeps --multi-release 24 --ignore-missing-deps --print-module-deps
→ modules racines calculés
→ jpackage --add-modules <modules>
→ runtime/bin/java --list-modules
→ contrôle des racines
→ assertion java.xml
```

La liste effective est conservée dans `RUNTIME-MODULES.txt` et reportée dans `VERSION` via `runtimeModules=`.

## P0 — MCP packagé comme gate de release

La qualification exige un vrai dialogue MCP :

```text
initialize
notifications/initialized
tools/list
```

avec vérification d'outils connus (`minos_search_code`, `minos_impact`). Un simple `MINOS --version` ne suffit plus.

## P0 — smoke setup isolé

Le setup de production n'est pas installé automatiquement pendant un smoke local. Le builder génère un setup non publiable avec :

- AppId distinct ;
- hooks PATH neutralisés ;
- configuration MCP neutralisée ;
- Docker neutralisé ;
- cleanup global neutralisé ;
- aucun prompt ni purge du répertoire utilisateur réel `%LOCALAPPDATA%\MINOS`.

Ainsi, une validation locale ne doit pas modifier l'installation MINOS réelle du mainteneur.

## P1 — Mode MCP exclusif et backend transactionnel

Le parcours courant est :

```text
Bienvenue
→ Dossier d'installation
→ Tâches Windows (PATH)
→ Mode MCP
     ( ) MCP natif Windows — recommandé
     ( ) MCP Docker — isolation renforcée
     ( ) Ne pas configurer maintenant
→ Clients IA                         [si un backend est choisi]
→ Racine projets Docker              [si Docker est choisi]
→ Prêt à installer
```

**Un seul backend est actif à la fois.** Le backend déjà persisté dans `%LOCALAPPDATA%\MINOS\data\runtime\backend.properties` est présélectionné lors d'un upgrade.

Les clients IA ne dépendent plus du backend : Copilot JetBrains/IntelliJ, Copilot CLI, Claude Code, Claude Desktop et Codex CLI/Desktop utilisent toujours :

```text
command = <installation>\app\minos.exe
args    = mcp
env     = MINOS_HOME=%LOCALAPPDATA%\MINOS\data
```

Le choix `native|docker` est résolu derrière ce point d'entrée stable. Changer de backend ne réécrit pas les configurations clientes.

Si Docker est explicitement choisi mais que Docker Desktop/daemon est indisponible, le Wizard bloque et demande de corriger le prérequis ou de revenir choisir un autre mode. Il n'existe **aucun fallback silencieux** vers le backend natif.

## P1 — switching transactionnel

`scripts/install/switch-mcp-backend.ps1` applique :

```text
prepare
→ validate
→ handshake
→ commit backend.properties
→ retire ancien backend
```

Le handshake passe par `minos.exe mcp` dans un `MINOS_HOME` candidat isolé et exige `initialize` + `tools/list`. Le fichier `backend.properties` n'est committé qu'après succès.

Rollback :

- échec avant commit : backend actif inchangé ;
- échec après commit : restauration des octets précédents de `backend.properties` ;
- échec d'un vrai upgrade Docker : restauration du runtime/marker précédent puis redémarrage de l'ancien Docker.

Un runtime Docker géré correspondant exactement au package courant est réutilisé via `Start + Validate + handshake`, sans reconstruire l'image lors d'un simple retour native→Docker.

## P1 — Wizard clients IA détectés

Lorsque **native ou Docker** est choisi, la page **Clients IA** affiche les intégrations détectées. Les clients indisponibles sont désactivés et une raison est affichée.

Préflight :

- GitHub Copilot JetBrains / IntelliJ : détection application/config ;
- GitHub Copilot CLI : capability probe, rejet des launchers VS Code incompatibles ;
- Claude Code : capability probe MCP ;
- Claude Desktop : détection application/config ;
- OpenAI Codex : capability probe CLI ou mode Codex Desktop/config utilisateur.

Les clients MCP ne sont pas des entrées statiques `[Tasks]` Inno Setup.

## P1 — Codex Desktop

Lorsque le préflight choisit le mode Desktop, MINOS gère un bloc marqué dans :

```text
%USERPROFILE%\.codex\config.toml
```

Le bloc est sauvegardé, idempotent et ownership-aware. Une section `mcp_servers.minos` non gérée n'est jamais écrasée.

## P1 — ZIP backend-aware et upgrade rollback-safe

`install.ps1` accepte :

```text
-McpBackend none|native|docker
```

Pour Docker, `-ProjectsRoot` est obligatoire. Le ZIP sauvegarde l'installation programme précédente avant remplacement. Si le nouveau payload ou la validation du backend échoue, l'ancien répertoire est restauré. Les noms de backup incluent les millisecondes pour éviter les collisions lors d'upgrades rapprochés.

## P1 — désinstallation MCP et données locales

La désinstallation :

- utilise les chemins CLI sauvegardés lorsque possible ;
- conserve les entrées préexistantes ;
- conserve les entrées gérées modifiées par l'utilisateur ;
- supprime uniquement les intégrations encore identifiables comme appartenant à MINOS ;
- arrête/supprime le runtime Docker géré sans supprimer implicitement ses données persistantes ;
- conserve **par défaut** `%LOCALAPPDATA%\MINOS` ;
- propose explicitement, lors d'une désinstallation interactive, de supprimer aussi tout `%LOCALAPPDATA%\MINOS` ;
- affiche un avertissement irréversible et positionne le choix par défaut sur **Non / conserver** ;
- ne pose aucun prompt et ne purge aucune donnée utilisateur réelle pendant les smoke/silent uninstall automatisés.

La purge complète optionnelle supprime notamment projets enregistrés, snapshots, états d'indexation, providers gérés, logs, backups et données Docker MINOS. Elle est effectuée après le cleanup normal de désinstallation.

## P2 — stderr MCP

Le shaded JAR de distribution inclut `slf4j-nop` afin d'éviter les warnings `SLF4J(W): No SLF4J providers were found.`. Ce point n'était pas la cause du crash 1.0.0, mais nettoie stderr pour les clients MCP STDIO.

## Gates utilisateur avant publication

La publication 1.0.1 reste bloquée jusqu'à validation explicite :

1. la page **Mode MCP** propose exactement natif, Docker ou aucun ;
2. un seul backend est sélectionnable à la fois ;
3. Docker explicitement choisi échoue clairement s'il est indisponible ;
4. la page **Clients IA** est commune aux backends natif et Docker ;
5. le faux Copilot CLI/shim est désactivé ;
6. JetBrains/Claude/Codex sont décrits conformément aux logiciels réellement présents ;
7. installation dans le répertoire attendu ;
8. `minos.cmd --version` retourne 1.0.1 ;
9. Copilot démarre `app\minos.exe mcp` sans `NoClassDefFoundError` ;
10. MCP atteint l'état Connected ;
11. les tools MINOS sont visibles ;
12. bascule native→Docker et Docker→native sans réécrire les clients ;
13. désinstallation standard conserve `%LOCALAPPDATA%\MINOS` lorsque **Non** est choisi ;
14. désinstallation avec purge supprime `%LOCALAPPDATA%\MINOS` lorsque **Oui** est choisi ;
15. désinstallation préserve les configurations tierces non détenues ;
16. autorisation explicite de publication.
