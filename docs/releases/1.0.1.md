# MINOS 1.0.1 — Windows Release Hardening

Statut : **CANDIDAT EN PRÉPARATION — NON PUBLIÉ**

Aucun tag `v1.0.1` ni aucune GitHub Release 1.0.1 ne doivent être créés avant qualification exact-head du nouveau candidat Windows et validation explicite de publication.

## Objectif

1.0.1 corrige le runtime Windows 1.0.0, intègre les capacités M29/M30 déjà livrées et applique le hardening post-audit avant publication.

Le périmètre courant comprend :

- runtime Java Windows dérivé du fat JAR réel avec `jdeps` ;
- MCP natif ou Docker autonome derrière le point d'entrée stable `minos.exe mcp` ;
- wizard Standard / Avancé ;
- stockage `local | postgresql` avec pgvector ;
- sémantique `disabled | local-hash | ollama` ;
- intégrations Copilot / Claude / Codex détectées ;
- lifecycle install/upgrade/switch/uninstall transactionnel ;
- supply-chain et scan de vulnérabilités bloquant.

## Runtime Java Windows complet

Le défaut 1.0.0 provenait d'une image `jpackage` trop étroite : `org.w3c.dom.Node`, fourni par `java.xml`, manquait au runtime embarqué.

Correction :

```text
fat JAR exact
→ JDK 24 jdeps --multi-release 24 --ignore-missing-deps --print-module-deps
→ modules racines calculés
→ jpackage --add-modules <modules>
→ runtime/bin/java --list-modules
→ contrôle des racines
→ assertion java.xml
```

La liste effective est conservée dans `RUNTIME-MODULES.txt` et reportée dans `VERSION`.

## MCP packagé comme gate de release

La qualification exige un vrai dialogue MCP :

```text
initialize
notifications/initialized
tools/list
```

avec vérification d'outils MINOS connus. Un simple `--version` ne constitue pas une preuve du runtime MCP.

## Backend MCP M29

M29 est terminé et la parité native/Docker a été qualifiée jusqu'à M29-S8. Le contrat durable reste :

```text
Copilot / Claude / Codex
          ↓
     minos.exe mcp
          ↓
     backend router
       /       \
    native     docker
```

Le wizard propose exactement un choix actif :

```text
MCP natif Windows — recommandé
MCP Docker — isolation renforcée
Ne pas configurer maintenant
```

Docker explicitement sélectionné mais indisponible bloque l'installation ; aucun fallback silencieux vers le natif n'est autorisé.

`scripts/install/switch-mcp-backend.ps1` conserve la transaction :

```text
prepare
→ validate
→ handshake
→ commit backend.properties
→ retire ancien backend
```

Un échec avant ou après commit restaure l'état précédent selon le point de défaillance.

## Wizard Standard / Avancé M30

Le wizard expose deux niveaux :

```text
Standard — recommandé
Avancée
```

En avancé, les axes sont indépendants :

```text
runtime MCP   : native | docker | none
stockage      : local | postgresql
sémantique    : disabled | local-hash | ollama
```

Le backend PostgreSQL est réel, versionné et utilise pgvector pour le ranking vectoriel. Le backend local reste disponible et aucun fallback silencieux PostgreSQL→local n'est autorisé.

Ollama peut être :

- une instance loopback existante lorsque MINOS tourne en natif ;
- un sidecar Docker géré par MINOS lorsque le backend Docker est utilisé.

Le query plane Docker reste isolé. Le téléchargement d'un modèle Ollama géré n'obtient qu'un egress temporaire pendant le provisioning.

## Clients IA

La page **Clients IA** affiche les intégrations disponibles avec diagnostic visible. Les cases indisponibles restent désactivées.

Sur le wizard 1.0.1 :

- GitHub Copilot — JetBrains / IntelliJ ;
- GitHub Copilot CLI ;
- Claude CLI / Claude Code ;
- Claude Desktop ;
- OpenAI Codex CLI ;
- OpenAI Codex Desktop.

Le faux launcher Copilot de VS Code est rejeté avant capability probe.

Codex CLI et Codex Desktop sont détectés séparément. Ils ciblent cependant la même intégration MCP nommée ; le wizard refuse donc leur sélection simultanée et configure explicitement le mode `cli` ou `desktop` choisi.

Les clients utilisent toujours :

```text
command = <installation>\app\minos.exe
args    = mcp
env     = MINOS_HOME=<data-root>
```

Changer de backend MCP ne réécrit pas les configurations clientes.

## Résumé avant installation

Avant l'installation, le wizard affiche le récapitulatif des choix et des composants effectivement gérés :

- type Standard / Avancé ;
- programme et data roots ;
- backend MCP ;
- nom du serveur MCP ;
- stockage ;
- provider sémantique ;
- clients IA sélectionnés ;
- runtime MCP Docker éventuel ;
- PostgreSQL/pgvector Docker éventuel ;
- Ollama Docker éventuel ;
- téléchargement/provisionnement du modèle Ollama lorsque demandé.

Ce comportement reprend le pattern utile du Windows deployment wizard de NEXUS Context Engine sans remplacer les invariants MINOS de backend exclusif, ownership et rollback.

## Sécurité des dépendances

Le hardening post-audit bloque la publication avec des versions Jackson vulnérables connues.

MINOS utilise deux générations :

```text
Jackson 2  → backend PostgreSQL / codecs MINOS
Jackson 3  → SDK MCP 2.x
```

Les versions centrales de qualification sont :

```text
Jackson 2 : 2.22.1
Jackson 3 : 3.1.5
```

La CI exécute un **OSV Scanner** avec `fail-on-vuln=true`. Une vulnérabilité connue détectée par ce gate bloque le candidat jusqu'à correction ou décision de sécurité explicitement documentée.

## PostgreSQL/pgvector fail-closed en qualification

Le développement local peut encore ignorer les tests d'intégration PostgreSQL lorsque Docker n'est pas disponible. En CI/release, la propriété :

```text
-Dminos.postgresql.tests.required=true
```

rend Docker/pgvector obligatoire : l'impossibilité de démarrer le conteneur devient un échec de build, jamais un skip silencieux.

La configuration Docker Desktop Testcontainers n'est injectée que sous Windows ; Linux découvre son socket Docker normalement.

## Couverture

Le gate JaCoCo couvre désormais explicitement les responsabilités M29/M30 :

- backend routing M29 ;
- configuration/selection du storage backend M30 ;
- backend PostgreSQL/pgvector M30.

## Qualification du HEAD résultant

La validation principale s'exécute :

- sur pull request vers `develop` ou `main` ;
- également sur `push` de `develop` ou `main` afin de requalifier le HEAD réellement intégré.

Le candidat final doit donc être qualifié après merge, pas seulement via un merge-ref de PR.

## Smoke setup isolé

Le setup smoke utilise un AppId distinct et neutralise les mutations globales : PATH, intégrations MCP, runtime Docker, purge utilisateur. La qualification ne doit pas modifier l'installation MINOS réelle du mainteneur.

## Désinstallation

La désinstallation :

- supprime uniquement les intégrations toujours identifiables comme appartenant à MINOS ;
- conserve les configurations tierces et les entrées gérées modifiées par l'utilisateur ;
- arrête le runtime Docker géré sans supprimer automatiquement ses données ;
- conserve par défaut `%LOCALAPPDATA%\MINOS` ;
- propose explicitement la purge complète en mode interactif ;
- positionne la réponse par défaut sur **Non / conserver** ;
- ne purge pas les données d'une base PostgreSQL externe.
