### AUD-QUA-01

**Les trois surfaces (explorateur, API, MCP) traduisent toute IllegalArgumentException en erreur d'usage sans rien journaliser : un bogue interne s'affiche comme « requête invalide »**

- **Statut au 25/11** : Fermé avec réserve · **Changement** : PR #759 (distinguer-l-erreur-d-usage-de-l-echec-interne) et PR #762 (explorateur), archivés
- **Historique** : Fermé avec réserve (17/11) → Fermé avec réserve (19/11) → Fermé avec réserve (20/11) → Fermé avec réserve (25/11)
- **Sévérité** : Moyenne · **Axes** : Qualité · **Effort** : M · **Confiance** : confirmé
- **Sprint** : 3 · **Dépend de** : aucun · **Débloque** : aucun
- **Preuve d'origine** : minos-explorer/src/main/java/com/minos/explorer/ExplorerApi.java:133-135 (`catch (IllegalArgumentException usage) { return Answer.error(400, "INVALID_REQUEST", PublicErrorMessages.sanitize(...)) }`, aucun appel à `failures`) ; minos-api/src/main/java/com/minos/api/MinosApiSupport.java:70-71 et :106-107 (IAE -> INVALID_REQUEST, ISE -> UNAVAILABLE) ; minos-mcp/src/main/java/com/minos/mcp/MinosMcpTools.java:195-196 (IAE -> clientError, alors que :207 journalise les autres échecs). Sous-classes JDK d'IAE avalées de la même façon : NumberFormatException, InvalidPathException, PatternSyntaxException, IllegalFormatException.
- **Impact** : Une InvalidPathException sur un nom de fichier corrompu ou une précondition violée dans un service arrive à l'utilisateur en 400 / INVALID_REQUEST, avec un message nettoyé, et sans aucune trace côté serveur. Le bogue n'est pas vu et le diagnostic part sur une fausse piste (« corrigez votre requête »). C'est le schéma de requalification du 10/10 (AUD-QUA-03), cette fois sur les surfaces, et il est reconduit dans le nouveau minos-explorer.
- **Action** : Introduire un type d'erreur d'usage explicite (par ex. `UsageException` dans minos-application, levé par les validations de paramètres et par ProjectResolver) et ne mapper en 400 que ce type. Une IAE ou ISE résiduelle doit suivre la voie interne (500 opaque + journal du type et de la cause racine, comme MinosMcpTools.logInternalFailure). Ajouter un test par surface : une IAE levée par le service donne 500 et une ligne de journal.
- **Vérification (19/11)** : Inchangé depuis le 17/11 (MinosApiSupport.java identique). UsageException reste le seul type rendu comme erreur d'usage par les trois surfaces dans execute. Le reste localisé est toujours là : l'ouverture d'une façade de l'API Java traduit toute IllegalArgumentException en INVALID_REQUEST. Preuve : diff 182ae1df..acd79cb8 de minos-api/src/main/java/com/minos/api/MinosApiSupport.java -> vide ; MinosApiSupport.java:148-151 (`catch (IllegalArgumentException exception)` -> LOGGER WARNING diagnosticSummary puis publicFailure(ErrorCode.INVALID_REQUEST, exception)).
- **Réserve** : MinosApiSupport.openApplication (MinosApiSupport.java:148-151) traduit encore toute IllegalArgumentException levée à l'ouverture en INVALID_REQUEST, journalisée par sa seule classe, sans trace. L'écart à l'action est voulu par le code (commentaire :149), sans décision écrite.
- **Désaccord avec le suivi** : SUIVI.md:58 ne mentionne pas le reste de MinosApiSupport.openApplication.
- **Origine** : AUD-QUA-03 (10/10), même schéma de requalification étendu aux surfaces
