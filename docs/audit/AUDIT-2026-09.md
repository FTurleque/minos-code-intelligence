- les entrées sont bornées partout ;

## 3. Architecture et couplage

### A1 — L'indexation distante est désactivée de fait (🔴 CONFIRMÉ)
- **Où** : `WorkerSandboxBackends.strongestAvailable`, `WorkerSandboxQualification`, `LinuxBubblewrap…`, `WindowsAppContainerWorkerSandboxBackend.containment()`.
- **Constat** : les deux backends déclarent `filesystemWriteBytes/Entries = SUPERVISED_HARD_KILL`. La qualification les rétrograde donc en `UNTRUSTED_CODE_UNSUPPORTED`, et `LocalIsolatedIndexWorker` (indexation distante, CLI `remote`) échoue en mode fermé sur **tous** les OS. C'est même verrouillé par le test `currentOsBackendsFailClosedUntilStorageIsOsEnforced`.
- **Impact** :
  - environ 2 000 lignes de code sandbox sont inatteignables en production ;
  - le README annonce une « sandbox OS worker réelle qualifiée Linux + Windows » (#98) ;
  - le repli se fait en silence, sans aucun log.
- **Recommandation** : soit appliquer le quota de stockage au niveau OS (quota XFS/btrfs, tmpfs de taille fixe dans bwrap, VHD à taille fixe sous Windows), soit corriger la documentation. Dans les deux cas, journaliser la raison du repli.

### A2 — Application couplée aux adaptateurs (🔴 CONFIRMÉ)
- `minos-application` dépend dans son POM de `runtime-local`, `storage-local`, `provider-scip` et `integration-git`.
- `MinosApplicationAssembler` et `LocalStorageBackend` instancient directement `ManagedScip*`, `FileHostedControlPlaneStore`, `FileSymbolSnapshotStore`, `FileSemanticVectorStore`, etc.
- Des adaptateurs fichiers vivent dans le module application lui-même : `FileProjectFingerprintSnapshotStore` (≈580 lignes), `FileIndexStateStore`, `LocalProjectRegistry`.
- `ProviderPlatformService` dépend de `ScipIndexerCatalog.qualifiedM24Providers()`.
- `SemanticIndexService` fait des `instanceof LocalHash/Ollama`.
- `minos-storage-postgresql` dépend de `minos-application` : un adaptateur dépend du cœur applicatif.
- **Recommandation** : déplacer la racine de composition vers `minos-app`, garder dans `minos-application` uniquement des ports (interfaces), et déplacer les adaptateurs fichiers dans `storage-local`. Il faut aussi que `check-module-boundaries.py` interdise `application → adaptateurs`.

### A3 — Packages éclatés entre modules et doublons (🟠 CONFIRMÉ)
- 9 packages sont éclatés entre plusieurs modules, dont :
  - `com.minos.cli` (app, cli) ;
  - `com.minos.dynamic` (application, domain, engine) ;
  - `com.minos.hosted` (application, domain, engine) ;
  - `com.minos.runtime` (application, runtime-local) ;
  - `com.minos.store` (engine, storage-local).
- Conséquences : le projet ne peut pas passer à JPMS, et la visibilité « package » traverse les modules.
- `cli.ProjectOperations`, `cli.ProjectSymbolQuery`, `cli.LocalProject*` sont des alias dépréciés, mais `MinosCliRunner` les instancie encore. La dépréciation ne peut donc jamais aboutir.

### A4 — Classes-dieux et constructeurs télescopiques (🟠 CONFIRMÉ)
- `MinosApplication` expose environ 30 services.
- `LocalProjectArchitectureQuery` a 9 constructeurs et recalcule la découverte, le snapshot et la topologie à chaque appel, sans cache.
- `MinosCli` a 9 constructeurs.
- Les plus gros fichiers : `WindowsAppContainerWorkerSandboxBackend` (789 lignes), `SnapshotBinaryCodecSupport` (757), `FileProjectFingerprintSnapshotStore` (728), `DistributedArtifactBundleStore` (706).

### A7 — Le script de frontières ne se confronte jamais au reactor (🟡 CONFIRMÉ, résidu d'A2)
La liste des modules est codée en dur dans `check-module-boundaries.py` et n'est jamais comparée aux `<modules>` du POM racine. Le contrôle existant vérifie que la politique couvre cette liste, pas que la liste couvre le reactor : un module ajouté au projet et oublié dans le script échappe à toutes les règles, POM comme sources.

### A8 — Le choix du backend de stockage utilise le chargeur de classes de contexte (🟡 CONFIRMÉ, résidu d'A2)
`ServiceLoader.load(StorageBackendProvider.class)` est appelé sans chargeur explicite dans la composition : le résultat dépend du chargeur de contexte du thread. C'est exactement le défaut corrigé pour la découverte de la racine de composition, non étendu à la sélection du backend. Le code a été déplacé tel quel, donc le défaut est préexistant, mais il vit désormais dans le module de composition.

### A9 — Le snapshot reste chargé intégralement en mémoire (🟠 CONFIRMÉ, résidu d'A6)
Le lot A6 a traité le format sur disque, le plafond et la recherche hybride, mais **aucun gain mémoire n'est revendiqué** : `InMemoryCodeKnowledgeStore` charge toujours un snapshot en entier. La pagination ou le mappage mémoire fait l'objet de l'ADR 0047, laissé en `Proposed` — c'est une refonte, pas une correction. Le plafond rend au moins la limite explicite avant l'ingestion au lieu de la faire découvrir après.

### A11 — Trois points d'entrée publics n'isolent rien (🟡 CONFIRMÉ, relevé au sprint 9)
Relevé en prouvant que le plan admin ne compile pas de code non fiable : trois entrées publiques de `minos-runtime-local` n'appliquent aucune isolation et exécuteraient du code venu d'un projet indexé si elles étaient câblées. Aucun appelant en production aujourd'hui — un seul site de construction, la variante complète — mais rien n'empêche un futur appel. À rendre non publiques ou à retirer.

### A10 — Les chemins de source approchent les limites de l'outillage Windows (🟡 PLAUSIBLE, effet de bord d'A3)
Ranger chaque module sous son propre préfixe de package allonge les chemins : `com/minos/storage/local/store/<classe>.java` descend à neuf répertoires sous la racine, auxquels s'ajoute `target/` au build. Aucun échec observé à ce jour, mais la marge avant la limite historique de 260 caractères de Windows se réduit, et des outils tiers refusent déjà ces profondeurs. À surveiller au premier échec de build Windows portant sur un chemin.

### A5 — `minos-engine` fourre-tout (🟡 CONFIRMÉ)
- Le package `io` (primitives de sécurité et d'I/O) vit dans le module moteur.
- Deux modèles de capacités coexistent, `IndexerDescriptor.capabilities` et `ProviderCapabilityProfile`, avec un risque de dérive.
- Le domaine mélange des conventions : lignes numérotées à partir de 0 dans `SemanticDocument`, à partir de 1 dans `SymbolLocation`.
- `SemanticVectorStore` (domaine) embarque de l'I/O.

### A6 — Mémoire et scalabilité (🟠 PLAUSIBLE)
- Les snapshots sont chargés entièrement en mémoire (`InMemoryCodeKnowledgeStore`, cache de 512 Mo).
- Les chaînes sont encodées en UTF-16, ce qui double leur taille.
- Le plafond des snapshots persistés (256 Mo) est inférieur à la limite des artefacts SCIP (512 Mo) : sur un gros projet, l'échec arrive tard.
- `HybridSearchService` re-normalise tout le corpus (jusqu'à 250 000 documents) à chaque requête de 64 Ko au plus.
- `ImpactAnalysisService` n'applique `maxResults` qu'après une traversée complète.


## 4. Fiabilité opérationnelle et distribution

### R1 — Aucune reprise après une indexation interrompue (🔴 CONFIRMÉ)
- **Où** : `orchestration/IndexingRunExecutor`, `AuthoritativeProjectStateReconciler.recoverAbandonedRuns`, `runtime-local/RunDirectoryRetention`.
- **Constat** : tout run `RUNNING` retrouvé sous bail exclusif est finalisé en `FAILED` sans consulter le disque, et la relance tire un nouveau `runId`. Or les artefacts `runs/<runId>/<indexerId>/index.scip` sont écrits atomiquement, avec fsync, et ne sont jamais supprimés en fin de run. Le travail coûteux est donc encore là, mais personne ne le regarde. S'y ajoutent trois trous : le point de contrôle ne porte ni le module, ni la version du provider, ni l'empreinte de l'artefact ; la rétention des répertoires de run peut effacer le run à reprendre, et elle se déclenche au début de l'exécution suivante ; les snapshots `.tmp` orphelins ne sont nettoyés par personne.
- **Scénario** : un reboot pendant l'indexation d'un monorepo, au dernier module de sept providers, coûte la totalité du run.
- **Conception** : [ADR 0039](../adr/0039-reprise-indexation-apres-interruption.md) — points de contrôle par cible, état `INTERRUPTED`, reprise sur le même `runId`.

### D1 — Le paquet n'embarque aucun indexeur (🟠 CONFIRMÉ) — ✅ **clos au sprint 9, avec réserve**
- **Où** : `scripts/release/build-windows-distribution.ps1`, `packaging/windows/minos-installer.iss.template`.
- **Constat** : la distribution ne contient que l'image `jpackage` (runtime Java + `minos.jar`), les scripts d'intégration, le SBOM et les notices. Le `README.txt` généré demande encore `minos.cmd tools install scip-java`, et le template Inno Setup n'a aucune étape d'installation d'outil. L'image Docker release, elle, embarque déjà ses toolchains avec des téléchargements vérifiés.
- **Scénario** : sur un poste neuf, ou sans accès réseau, MINOS s'installe correctement puis échoue à indexer quoi que ce soit.
- **Conception** : [ADR 0040](../adr/0040-distribution-auto-portante-indexeurs-embarques.md) — indexeurs embarqués, amorçage hors ligne, repli par téléchargement épinglé.


### D3 — Trois vérifications de la distribution n'ont jamais été exécutées (🟡 CONFIRMÉ, résidu du sprint 9)
La coupure réseau **physique** n'a pas été faite : la preuve hors ligne repose sur un observateur réseau avec témoins positifs, pas sur une machine déconnectée. L'installateur Windows de bout en bout n'a jamais été exécuté. Et la qualification réelle de mise à niveau Docker n'a pas tourné : elle exercera pour la première fois la migration des noms de compose depuis une vraie release antérieure. S'y ajoutent les ponts de tolérance à l'ancien nom, à retirer quand plus aucune installation ne les porte.

### R4 — La promotion reprise ne vérifie pas que le snapshot préparé couvre les cibles courantes (🟠 CONFIRMÉ, résidu de R1) — ✅ **clos au sprint 6**
La reprise directe en promotion exige seulement que rien ne reste à exécuter, que la phase soit `PROMOTION` et qu'un snapshot soit préparé ; elle ne compare jamais les cibles réutilisées à celles du run interrompu. Scénario : run interrompu en promotion sur deux scopes, l'utilisateur supprime un module, relance ; la découverte ne négocie plus que le scope restant, dont le point de contrôle est valide, et MINOS promeut le snapshot qui contient encore l'index du module supprimé — un index qu'un run complet n'aurait jamais produit. Exiger l'égalité des clés de cible, sinon re-préparer.

### R5 — La rétention peut encore supprimer un run reprenable (🟠 CONFIRMÉ, résidu de R1) — ✅ **clos au sprint 6**
Trois défauts dans la même méthode : `overCount` devient vrai pour **chaque** entrée dès que le parcours de `runs/` est tronqué, marqueur `.resumable` compris ; seul le run du processus courant est protégé, donc une seconde indexation concurrente peut effacer le répertoire de run de la première ; et un run marqué expire à 24 h quand un run ordinaire vit 7 jours — marquer un run interrompu divise sa durée de vie par sept au lieu de la prolonger.

### R6 — Une interruption pendant l'attente de l'artefact dégrade le run en FAILED (🟡 CONFIRMÉ, résidu de R1) — ✅ **clos au sprint 6**
L'attente de lisibilité rétablit bien le drapeau d'interruption, mais lève une exception sans cause ; la détection d'interruption remontant `getCause()`, elle conclut à un échec ordinaire. Un arrêt du service dans la seconde qui suit la sortie d'un provider jette donc tous les points de contrôle déjà acquis. `ResumeAborted` ne chaîne pas davantage sa cause.

### R7 — La réparation « snapshot stable » perd la référence de run reprenable (🟡 CONFIRMÉ, résidu de R1) — ✅ **clos au sprint 6**
Cette branche du réconciliateur réécrit l'état projet sans `resumableRunId` et sans appeler `supersede`, contrairement aux autres chemins de récupération. Le run interrompu garde son marqueur : son répertoire échappe indéfiniment à la rétention, et il peut être re-proposé alors qu'il avait été supplanté.

### R2 — Un saut d'horloge peut faire conclure à tort à une réutilisation de PID (🟠 PLAUSIBLE, résidu de S3) — ✅ **clos au sprint 6**
La marque d'appartenance compare deux instants de démarrage dérivés de l'horloge murale (`ProcessHandle.Info.startInstant`, calculé depuis `btime`), avec une tolérance de 2 s. Un pas NTP décale cette base : deux JVM lisent alors un instant différent **pour le même processus**, la dérive dépasse la tolérance, et le balayeur conclut « pid réutilisé » puis tue le cgroup d'un MINOS vivant — le symptôme même de S3. Comparer les ticks de `/proc/<pid>/stat`, indépendants de l'horloge murale, ou ne jamais récupérer sur le seul écart d'instant.

### R3 — Les résidus cgroup non récupérables ne sont pas signalés (🟡 CONFIRMÉ, résidu de S3) — ✅ **clos au sprint 6**
`qualifyRoot` appelle `reclaimStaleJobs(root)` en jetant le `StaleSweep` retourné ; un résidu marqué laissé intact n'est journalisé qu'en DEBUG ; un cgroup non marqué encore peuplé (créé par une version antérieure) n'est désormais plus jamais récupéré. Ces résidus consomment `pids` et `memory` de la racine sans remonter nulle part. Le message d'échec de suppression journalise par ailleurs un chemin absolu, alors que le fichier affirme deux fois ne jamais en journaliser.

### R8 — Un snapshot préparé par un run tué reste sur disque pour toujours (🟠 CONFIRMÉ, découvert au sprint 6)
Les trois rétentions parcourent `symbol-snapshots/`, `fingerprint-snapshots/` et `runs/` ; aucune ne parcourt `staged-snapshots/`. Un run tué avant sa promotion laisse son snapshot préparé — potentiellement plusieurs centaines de mégaoctets — indéfiniment, de même que les fichiers temporaires d'un processus tué pendant une publication d'empreinte. C'est l'exact inverse de ce qu'annonçait Q4 : une fuite, pas une suppression. À traiter sous le bail de cycle de vie, avec la durée de vie unique introduite au lot 1.

### R9 — Le verrou de rétention est le seul verrou du dépôt sans délai ni couche JVM (🟡 CONFIRMÉ, résidu du sprint 6) — ✅ **clos au sprint 8 avec S6**
`retention-locks/<projet>.lock` est un `FileChannel.lock()` sans délai, alors que tous les autres baux sont bornés à 10 s et que les gates interdisent `channel.lock()` ailleurs ; sans couche JVM (un second `compact` du même processus lèverait `OverlappingFileLockException` au lieu d'attendre), et ouvert sans `NOFOLLOW` ni droits privés, contrairement à S5. Sans danger aujourd'hui parce que son unique appelant tient déjà le bail — mais rien ne garde cette règle.

### R10 — Une lecture peut encore muter, par la migration des runs au format historique (🟡 CONFIRMÉ, résidu du sprint 6)
Le sprint a fermé « une lecture ne mute rien » pour l'état projet, mais l'ouverture du magasin déplace ou supprime les fichiers de run du format d'origine, sans bail : le processus qui répond à un simple statut écrit donc sur disque. Préexistant, idempotent et limité aux données historiques, mais la règle ne le couvre pas.

### R11 — Les cgroups marqués par un build antérieur ne sont plus jamais récupérés (🟡 CONFIRMÉ, conséquence assumée du sprint 6)
La marque porte désormais les inodes des espaces de noms PID et temps. Un cgroup marqué par un build `develop` antérieur ne peut plus prouver son appartenance : il n'est plus récupéré automatiquement, même à propriétaire mort. Ils sont signalés par le WARNING agrégé et la documentation dit comment les supprimer. Aucune version publiée n'écrit ces marques : le constat se ferme quand plus aucun de ces builds n'existe.

### R12 — Une commande de lecture ne peut pas tourner sur un `MINOS_HOME` en lecture seule (🟠 CONFIRMÉ, mesuré au sprint 7)
Le câblage paresseux a supprimé les écritures qui lui étaient imputables, mais deux subsistent sur le chemin de toute lecture : `MinosApplication.open` crée le squelette du stockage, et lire le registre crée et prend son verrou inter-processus. Un `MINOS_HOME` en lecture seule, un volume plein ou un montage partagé en lecture restent donc inutilisables, même pour un `project list`. Y remédier suppose un mode de stockage sans écriture ou un verrou de lecture sans fichier — c'est-à-dire de rouvrir le régime de verrous du sprint 6.

### R14 — L'indexation Java échoue sous le bac à sable AppContainer (🟠 CONFIRMÉ, mis au jour au sprint 9)
Sur un poste Windows, `minos index` d'un projet Java échoue sous le bac à sable alors que le même runner appelé directement réussit. Une première cause était une régression du sprint 8 — la DACL protégée de `runtime\` empêchait le grant AppContainer d'atteindre le runner — corrigée dans une PR dédiée. La cause profonde reste : `C:\` n'est pas lisible par ALL APPLICATION PACKAGES, donc PowerShell 5.1 ne peut pas changer de répertoire courant sous AppContainer. C'est ce qui empêche de prouver D1 sur Java. S'ajoutent deux défauts de lisibilité : le message final perd son détail, et le runner masque le vrai échec.

### R13 — Les répertoires de lanceurs s'accumulent et la désinstallation les laisse (🟡 CONFIRMÉ, résidu du sprint 8)
Le script du bac à sable a été sorti de `MINOS_HOME` vers `%LOCALAPPDATA%\minos-launchers\<sha256>\`, à un nom dérivé de son empreinte — le bon choix, mais il crée un répertoire par version du script, sans ménage, et le désinstalleur ne purge pas cet emplacement. Les copies d'un MINOS précédent sont supprimées au démarrage du bac à sable ; celles des versions qui ne tournent plus restent.

## 15. Sécurité

### S1 — Escalade ADMIN → OWNER (🔴 CONFIRMÉ)
- **Où** : `hosted/HostedMembershipService.grant` et `HostedTokenService.issue`.
- **Constat** : `grant` exige seulement `MEMBER_WRITE`, sans borner le rôle attribué par rapport à celui de l'appelant. Or `ADMIN` a toutes les permissions sauf `KEY_ROTATE` (`HostedRole`).
- **Scénario** : un ADMIN s'attribue `OWNER`, obtient `KEY_ROTATE` et peut révoquer les autres owners (`requireOwner` exige seulement qu'il reste au moins un owner). De la même façon, `TENANT_ADMIN` peut émettre un jeton au nom d'un OWNER.
- **Correctif** : interdire d'attribuer un rôle supérieur au sien et réserver l'attribution OWNER aux OWNER. Ajouter un test de non-régression.

### S2 — Saturation de l'audit par les refus (🔴 CONFIRMÉ)
- **Où** : `HostedAuthorizationService.authorizeMutation`, branche refusée.
- **Constat** : chaque refus persiste un événement `DENIED` et incrémente la version du tenant. Arrivé à `MAX_AUDIT_EVENTS`, `append` lève « hard capacity reached ».
- **Scénario** : un membre révoqué dont le jeton reste valide jusqu'à 24 h, ou un simple VIEWER, boucle sur des mutations refusées. Plus aucune mutation légitime ne passe, et les écritures concurrentes subissent des conflits de version optimiste.
- **Correctif** : limiter le débit des refus par principal, les agréger, ou les journaliser hors de la chaîne transactionnelle. Garder de la place réservée pour les mutations autorisées.

### S3 — Nettoyage cgroup inter-processus (🔴 CONFIRMÉ, impact PLAUSIBLE)
- **Où** : `runtime-local/LinuxCgroupJob.reclaimStaleJobs` et `relocateSelf`.
- **Constat** : au moment de la découverte, tout cgroup enfant `minos-*` qui contient encore des processus vivants est tué, sans vérifier à quel processus MINOS il appartient.
- **Scénario** : la CLI est lancée pendant qu'un serveur MCP indexe. La CLI tue les jobs `minos-<runId>-…` du serveur, et l'indexation échoue sans raison apparente.
- `relocateSelf` déplace aussi le processus entier dans `minos-controller`, un effet de bord global.
- Le profil bwrap n'a pas de seccomp.
- **Correctif** : préfixer les jobs par le PID ou un jeton d'instance, et ne récupérer que les cgroups dont le propriétaire est mort.

### S4 — Mot de passe PostgreSQL dans `toString()` (🔴 CONFIRMÉ)
- **Où** : `storage/StorageBackendConfiguration`.
- **Constat** : ce record contient `postgresPassword` sans redéfinir `toString()`. `safeDescription()` existe, mais rien n'oblige à l'utiliser.
- **Correctif** : redéfinir `toString()` pour masquer le mot de passe, ou encapsuler le secret dans un type `Secret` dont le `toString` affiche `***`.

### S5 — Durcissement du système de fichiers appliqué de façon inégale (🟠 CONFIRMÉ) — ✅ **clos au sprint 8**

Dans ces cas, des répertoires et fichiers sont créés avec les permissions par défaut ou ouverts sans `NOFOLLOW_LINKS` :

| Fichier / méthode | Défaut |
|---|---|
| `DistributedArtifactBundleStore` | `createDirectories`, `Files.write` manifeste, `copyBounded` |
| `LocalIsolatedIndexWorker`, `ProcessIndexerExecutor.prepareRunDirectory`, `BoundedProcessOutput.openTarget`, `RunDirectoryRetention` | permissions par défaut |
| `SharedCacheLeaseRegistry.openLeaseChannel`, `FileHostedControlPlaneStore.lock`, `LocalStorageRetentionService.compact`, verrou de matérialisation Git | `FileChannel.open(CREATE, WRITE)` sans NOFOLLOW |

`FileHostedControlPlaneStore.lock` et `LocalStorageRetentionService.compact` appellent `channel.lock()` sans délai, alors que le reste du code borne l'attente à 10 s. `compact` n'a pas non plus de verrou JVM, ce qui provoque une `OverlappingFileLockException` quand deux threads compactent en même temps.

### S14 — Le motif de refus de reprise est écrit sans assainissement (🟡 CONFIRMÉ, résidu de R1) — ✅ **clos au sprint 9**
`refusalReason` est concaténé tel quel dans la sortie texte et dans la sortie JSON de `minos index`, alors que tous les autres diagnostics de la commande passent par `publicDiagnostic`. Un motif qui embarquerait un chemin de run ou un message d'exception atterrirait sur stdout.

### S12 — La réserve d'audit compte tous les événements, pas seulement les refus (🟠 CONFIRMÉ, résidu de S2) — ✅ **déjà clos le 28/09 (`c380baa3`), l'audit était périmé**
La condition de chaînage d'un refus est `auditEvents().size() < deniedAuditCapacity()`, soit la taille **totale** de la chaîne. Un tenant qui accumule 90 % d'événements autorisés légitimes — la rétention n'évince rien implicitement — cesse de chaîner tout refus, y compris le premier refus d'une attaque réelle, qui se réduit alors à un WARNING. Compter les événements `DENIED` ferme le point.

### S13 — Un événement d'audit non chaîné est indiscernable d'un événement chaîné (🟡 CONFIRMÉ, résidu de S2) — ✅ **déjà clos le 28/09 (`f0f70b6d`), l'audit était périmé**
L'événement non chaîné sort du même `hash()`, avec la même clé, la séquence `auditSequence + 1` et le `previousHash` de la tête — valeurs que réutilisera le prochain événement chaîné. Rien dans l'événement sérialisé ne le distingue : un consommateur externe indexé par (tenant, séquence) voit une collision, et un événement non chaîné réinjecté dans un export vérifie son HMAC.

### S15 — MINOS réécrit l'ACL de son répertoire et y dépose un script exécutable (🟠 CONFIRMÉ, découvert au sprint 7) — ✅ **clos au sprint 8**
Sous Windows, la première commande qui ouvre l'application **supprime l'ACE de refus d'écriture** posée sur `MINOS_HOME` : une restriction explicite de l'administrateur est annulée en silence. Et `doctor` matérialise un script PowerShell exécutable (`sandbox/windows-appcontainer-sandbox-v4.ps1`) dans ce même répertoire. Les deux sont des comportements de durcissement, mais ils vont dans le sens inverse de S5 : le produit élargit ses droits sur son propre répertoire et y écrit du code. À trancher explicitement, puis à documenter.

### S16 — Ce que MINOS ne voit pas dans une ACL, il le supprime (🟡 CONFIRMÉ, limite assumée du sprint 8)
Une ACE de refus **conditionnelle** (`XD`) est invisible à `getAcl()` : la réécriture de la DACL l'emporte, alors que S15 vient d'établir que MINOS ne retire jamais une restriction d'administrateur. Même famille : une ACE `OWNER RIGHTS` (`S-1-3-4`) serait vue comme un grant étranger à retirer, échouerait, et le message brut du JDK nommerait le chemin. Et le backend AppContainer écrit encore des ACE hors de `PrivateLocalStorage`, donc hors de la règle « un seul endroit décide des droits ». Les lire demande un `icacls /save` par objet, ou un appel natif.

### S17 — Le gate d'E/S privées ne couvre pas cinq API d'écriture (🟡 CONFIRMÉ, résidu du sprint 8)
Le gate interdit les huit motifs demandés, mais `Files.newOutputStream`, `Files.createTempFile`, `Files.createDirectory`, `Files.copy` et `Files.newBufferedWriter` n'y figurent pas : rien n'empêche de réécrire une écriture brute sous `MINOS_HOME`. Les copies temporaires des magasins passent désormais par la primitive, mais par discipline et non par contrainte. Les ajouter exige de migrer d'abord les écritures de flux.

### S18 — Des chemins absolus subsistent dans les messages des primitives (🟡 CONFIRMÉ, résidu du sprint 8)
Le chantier n'a assaini que les messages qu'il touchait. Les autres nomment encore un chemin absolu, y compris dans `PrivateLocalStorage` — précisément le code qu'un opérateur lit quand quelque chose ne va pas. Même famille : `MinosRuntimeSettings.load` suit encore un lien avec `isRegularFile` avant d'appeler la primitive, qui le refuse ensuite avec un chemin dans le message.

### S19 — Un chemin collé à un caractère d'identifiant échappe à la détection (🟡 CONFIRMÉ, résidu du sprint 9)
L'heuristique qui repère un chemin dans un message ignore le cas où il est collé à un caractère d'identifiant — y compris une séquence ESC `[31m` immédiatement suivie du chemin. Le chemin passe alors la détection et atteint la sortie. Le cas est étroit mais il porte sur la dernière barrière avant stdout.

### S11 — Chaîne d'approvisionnement et conteneurs (🟠 CONFIRMÉ) — ✅ **clos au sprint 9 ; le point « code non fiable » était une prémisse fausse**
- Dependabot n'a pas d'écosystème `docker` : les digests de base et le snapshot APT ne sont jamais mis à jour.
- Les lockfiles npm SCIP ne sont pas suivis.
- `pgvector` et `ollama` sont épinglés par tag, pas par digest.
- Aucun `mem_limit`, `pids_limit` ni `cpus` dans les fichiers compose.
- Le plan `minos-admin` compile des projets non fiables avec accès réseau, en écriture sur tout `MINOS_DATA_DIR`, sans sandbox forte (conséquence de A1).
- Ollama tourne en root.
- L'image release embarque un JDK et 5 toolchains, soit une grosse surface d'attaque.
