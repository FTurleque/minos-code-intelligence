## Capacités livrées

MINOS 1.0.0 consolide notamment :

- indexation et snapshots structurés persistants ;
- recherche symbolique, références, dépendances, impact et architecture ;
- plateforme de providers et discovery explicite ;
- provider Java avancé : CFG, def-use, flux interprocéduraux bornés et primitives de sécurité ;
- retrieval sémantique/hybride local optionnel ;
- providers polyglottes C/C++, C#, Go et Rust avec dispositions/capabilities explicites ;
- indexation remote/distribuée sur révisions immuables ;
- observations runtime partielles corrélées au snapshot statique ;
- contrôle tenant / Team-Hosted embarqué et local-first ;
- surfaces CLI, API Java, MCP read-only et plugin IntelliJ ;
- packaging Windows natif avec setup.exe et ZIP portable ;
- SBOM CycloneDX, notices tierces et sidecars SHA-256.

## Défaut Windows MCP découvert après publication

L'audit post-publication a démontré que l'image Java embarquée par le packaging Windows était construite avec une liste de modules `jpackage` trop étroite.

Le serveur MCP natif peut échouer au bootstrap avec :

```text
java.lang.NoClassDefFoundError: org/w3c/dom/Node
```

`org.w3c.dom.Node` appartient au module JDK `java.xml`. Le problème ne vient pas de Copilot ni de la configuration MCP : le processus MINOS est lancé, puis son runtime Java embarqué ne contient pas toutes les capacités JDK demandées par le JAR final et ses dépendances.

Le gate 1.0.0 n'a pas détecté le défaut parce qu'il vérifiait notamment `minos --version`, l'installation et la désinstallation, mais n'exigeait pas un handshake MCP sur le binaire packagé.

### Disposition

- ne pas modifier ni retagger `v1.0.0` ;
- ne pas remplacer les assets existants ;
- corriger dans **1.0.1** ;
- pour les intégrations MCP natives Windows, préférer le candidat/release 1.0.1 une fois qualifié et publié.

Voir [`1.0.1.md`](1.0.1.md).

## Limites produit conservées

- le worker remote natif ne revendique pas une sandbox OS pour code non fiable ;
- la politique réseau `DENY` reste fail-closed lorsqu'aucun backend OS qualifié ne peut la prouver ;
- le mode Team/Hosted reste une capacité embarquée/local-first et ne constitue pas un SaaS opéré ;
- le retrieval sémantique reste optionnel et ses résultats concernés restent `HEURISTIC` ;
- les observations runtime restent partielles et leur absence ne prouve jamais une absence d'exécution.

L'issue #98 conserve le suivi de l'isolation OS réelle Windows/Linux.
